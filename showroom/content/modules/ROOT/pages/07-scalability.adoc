= Scalability

CertChain is designed for horizontal scalability at multiple layers — from scaling individual components to adding entirely new organizations.

This section includes hands-on exercises. You'll use the *Terminal* tab and the *Git Repository* (Gitea) to make changes and observe ArgoCD syncing them to the cluster.

== Prerequisites

First, log in to OpenShift from the *Terminal* tab:

[.console-input]
[source,bash,subs="attributes"]
----
oc login {openshift_api_url} -u admin
----

When prompted, enter the password from your lab provisioning email (RHDP) or the one you set during installation.

Verify the CertChain namespaces are healthy:

[.console-input]
[source,bash,subs="attributes"]
----
for ns in certchain certchain-techpulse certchain-dataforge certchain-neuralpath; do
  echo "=== $ns ==="
  oc get pods -n $ns --no-headers | grep -v Completed | awk '{print $1, $3}'
done
----

Next, clone the project from Gitea so you can make GitOps-driven changes:

[.console-input]
[source,bash,subs="attributes"]
----
cd ~
git clone {gitea_url}/certchain/hyperledger-on-openshift-demo.git certchain-repo
cd certchain-repo
git config user.name "Lab User"
git config user.email "lab-user@local.demo"
----

== Horizontal Scaling

Fabric peers and orderers are standard Kubernetes Deployments, so scaling them is as simple as changing the replica count. Let's try it.

=== Important: ArgoCD Auto-Sync

CertChain's ArgoCD Applications have *automated sync* enabled. If you scale a deployment imperatively with `oc scale`, ArgoCD will detect the drift and revert it within minutes. To demonstrate manual scaling, you must first *pause auto-sync* on the target application.

=== Exercise: Scale verify-api (Stateless Service)

First, pause ArgoCD auto-sync so your manual changes stick:

[.console-input]
[source,bash,subs="attributes"]
----
oc patch application certchain-central -n openshift-gitops --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":null}}}'
----

Now scale verify-api to 3 replicas:

[.console-input]
[source,bash,subs="attributes"]
----
oc scale deployment verify-api -n {central_namespace} --replicas=3
----

Watch the pods come up:

[.console-input]
[source,bash,subs="attributes"]
----
oc get pods -n {central_namespace} -l app.kubernetes.io/name=verify-api -w
----

Press `Ctrl+C` once all 3 pods show `Running`. Open the *ArgoCD* tab — the `certchain-central` app now shows *OutOfSync* because the live replica count differs from Git.

Scale back and re-enable auto-sync:

[.console-input]
[source,bash,subs="attributes"]
----
oc scale deployment verify-api -n {central_namespace} --replicas=1
oc patch application certchain-central -n openshift-gitops --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":{"prune":true,"selfHeal":true}}}}'
----

[cols="1,2"]
|===
| Component | Scaling Notes

| *verify-api*
| Stateless — each replica connects to the same peer. OpenShift Service load-balances.

| *cert-admin-api*
| Each replica submits transactions independently to its org's peer.

| *cert-portal / course-manager-ui*
| Static frontends — scale freely, no backend state.

| *Chaincode (CcaaS)*
| Deployed as a Kubernetes Deployment — scale replicas for concurrent endorsement execution.
|===

=== Exercise: Scale a Peer

Each organization runs a single peer. Pause ArgoCD and scale TechPulse to 2 peers:

[.console-input]
[source,bash,subs="attributes"]
----
oc patch application certchain-techpulse -n openshift-gitops --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":null}}}'
----

[.console-input]
[source,bash,subs="attributes"]
----
oc scale deployment peer0 -n {central_namespace}-techpulse --replicas=2
----

[.console-input]
[source,bash,subs="attributes"]
----
oc get pods -n {central_namespace}-techpulse -l app.kubernetes.io/name=peer0 -w
----

Each peer replica maintains a full copy of the ledger via gossip sync, can independently endorse transactions, and is load-balanced by the Kubernetes Service.

Scale back and re-enable auto-sync:

[.console-input]
[source,bash,subs="attributes"]
----
oc scale deployment peer0 -n {central_namespace}-techpulse --replicas=1
oc patch application certchain-techpulse -n openshift-gitops --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":{"prune":true,"selfHeal":true}}}}'
----

=== Scaling Orderers

The orderer cluster uses SmartBFT consensus with 4 nodes (tolerating 1 Byzantine fault). Adding orderers requires channel configuration updates — it's not a simple replica scale:

[cols="1,1,1"]
|===
| Orderers | Faults Tolerated | Notes

| 4 (this demo)
| 1
| Default — one orderer per org + central

| 7
| 2
| Add 3 orderers, update `configtx.yaml` consenter set

| 10
| 3
| Add 6 orderers, requires channel config update transaction
|===

== GitOps-Driven Scaling (ArgoCD)

The imperative approach above is great for learning. In production, you'd make changes in Git and let ArgoCD sync them — this is the GitOps way.

=== Exercise: Scale cert-admin-api via Git Push

Clone the repo from Gitea (if not done yet) and make a Git-driven change:

[.console-input]
[source,bash,subs="attributes"]
----
cd ~/certchain-repo
----

Edit the cert-admin-api Deployment to scale from 1 to 2 replicas:

[.console-input]
[source,bash,subs="attributes"]
----
sed -i 's/replicas: 1/replicas: 2/' helm/components/certchain-org/templates/cert-admin-api/deployment.yaml
----

Verify the change:

[.console-input]
[source,bash,subs="attributes"]
----
grep -n replicas helm/components/certchain-org/templates/cert-admin-api/deployment.yaml
----

Commit and push to Gitea:

[.console-input]
[source,bash,subs="attributes"]
----
git add helm/components/certchain-org/templates/cert-admin-api/deployment.yaml
git commit -m "feat: scale cert-admin-api to 2 replicas"
git push origin main
----

[TIP]
====
Gitea credentials: username `gitea`, password `openshift`.
====

Now open the *ArgoCD* tab ({argocd_url}[ArgoCD Dashboard^]) and observe:

. Click the **certchain-techpulse** Application tile
. Within ~3 minutes, ArgoCD detects the Git change and starts syncing
. The `cert-admin-api` Deployment shows **OutOfSync** → **Syncing** → **Synced**
. A second `cert-admin-api` pod appears

Watch from the terminal:

[.console-input]
[source,bash,subs="attributes"]
----
oc get pods -n {central_namespace}-techpulse -l app.kubernetes.io/name=cert-admin-api -w
----

[NOTE]
====
Since the org chart is shared across all 3 organizations, this change scales cert-admin-api in DataForge and NeuralPath too. In a real deployment, you'd use per-org values overrides.
====

Revert the change:

[.console-input]
[source,bash,subs="attributes"]
----
cd ~/certchain-repo
git revert HEAD --no-edit
git push origin main
----

== Adding a New Organization

The App-of-Apps Helm structure makes adding a 4th (or 5th, 6th...) organization straightforward. Each org is a parameterized instance of the same `certchain-org` Helm chart.

=== Architecture: How Orgs Are Created

The bootstrap chart at `helm/bootstrap/templates/applications.yaml` contains a loop that generates one ArgoCD Application per organization:

[source,yaml]
----
{{- $orgs := list "techpulse" "dataforge" "neuralpath" }}
{{- range $orgKey := $orgs }}
  # Creates: certchain-techpulse, certchain-dataforge, certchain-neuralpath
{{- end }}
----

Each org's config lives in `helm/bootstrap/values.yaml`:

[source,yaml]
----
components:
  techpulse:
    enabled: true
    org:
      name: techpulse
      displayName: TechPulse Academy
      mspId: TechPulseMSP
      primaryColor: "#2563eb"
----

=== What It Takes to Add "QuantumLeap"

To add a 4th organization called QuantumLeap, you would:

[arabic]
. *Add org config* to `helm/bootstrap/values.yaml`:
+
[source,yaml]
----
  quantumleap:
    enabled: true
    org:
      name: quantumleap
      displayName: "QuantumLeap Labs"
      mspId: QuantumLeapMSP
      primaryColor: "#dc2626"
----

. *Add org to the loop* in `helm/bootstrap/templates/applications.yaml`:
+
[source,yaml]
----
{{- $orgs := list "techpulse" "dataforge" "neuralpath" "quantumleap" }}
----

. *Create org values override* at `helm/components/certchain-org/values-quantumleap.yaml`

. *Push to git* — ArgoCD detects the change and creates a new `certchain-quantumleap` Application

. *Update Fabric config* — The `configtx.yaml` needs the new org's MSP definition, and a channel configuration update transaction must be submitted to add it to the consortium

=== What Gets Auto-Generated

Each new org Application automatically deploys a full stack:

* **Blockchain**: Peer + CouchDB + Orderer (BFT node)
* **Application**: cert-admin-api + course-manager-ui
* **Identity**: Keycloak + Postgres
* **Infrastructure**: RBAC, ExternalName services, enrollment jobs

All in a dedicated `certchain-quantumleap` namespace — completely isolated from existing orgs.
